# 트러블슈팅: 랭킹 로직 개편

랭킹 로직은 두 번 개편했다.

| 단계 | 랭킹 기준 | 상태 |
|---|---|---|
| 1차 개편 | 조회수 → 시간당 조회수 증가속도(velocity) + 영상별 키워드 집계 | **폐기** (2부 참고) |
| 2차 개편 | 유튜브(쇼츠 위주)에서 **한 주제를 다룬 서로 다른 채널 수** | 현재 방식 |

1부는 1차 개편 과정의 기록이다. 2차 개편으로 랭킹 방식 자체는 폐기됐지만, 그때 겪은 문제(Gemini 한도, 마이그레이션, 스케줄러)는 지금도 유효해서 남겨둔다.

---

# 1부. 1차 개편: 조회수 → 증가속도 + 키워드 집계

## 배경

기존 메인 랭킹(`/`)은 YouTube 인기차트/Google Trends RSS에서 한 번 수집한 조회수·검색량 추정치를 그대로 정렬해 보여줬다. 이 방식은 두 가지 구조적 편향이 있었다.

1. **조회수 절대값 편향** — 업로드가 오래된 유명 가수 뮤비처럼 누적 조회수가 큰 콘텐츠가 항상 상위를 차지하고, 지금 막 튀어오르는 트렌드는 가려짐.
2. **영상 단위 편향** — 영상 하나가 전체 순위를 지배. 여러 영상·소스에 걸쳐 반복 언급되는 밈·음식 유행 패턴은 구조적으로 드러날 수 없음.

## 1. 조회수 → 증가속도(velocity) 랭킹 *(2차 개편에서 랭킹 기준으로는 폐기)*

**문제점**
`TrendItem`은 수집 시점에 한 번 스냅샷(조회수)을 찍고 끝나는 구조라, "지금 얼마나 빠르게 튀어오르는지"를 계산할 방법이 없었다.

**개선 결과**
같은 YouTube 영상을 추적 가능하게 스키마를 확장했다 (`TrendItem.youtubeVideoId` unique 필드 추가 + `VideoSnapshot` 테이블 신설). 매 수집 주기마다 추적 중인 영상의 조회수를 다시 가져와 `VideoSnapshot`으로 적재하고, 가장 오래된 스냅샷과 최신 스냅샷의 차이를 경과 시간으로 나눈 `velocityScore`(시간당 조회수 증가량)를 계산해 랭킹 정렬 기준으로 삼았다.

**흐름**
1. `videos.list chart=mostPopular`로 신규 영상 발견 + 최근 48시간 내 추적 중인 영상 ID를 배치로 재조회 (`videos.list?id=...`, 최대 50개씩).
2. 신규 영상이면 `TrendItem` 생성, 기존 영상이면 `VideoSnapshot`만 추가.
3. `recordSnapshotAndRecomputeVelocity()`가 최초/최신 스냅샷 간 경과 시간이 6분(`MIN_ELAPSED_HOURS`) 이상일 때만 `velocityScore`를 계산 — 너무 짧은 간격은 노이즈가 커서 제외.
4. **검증 중 발견한 함정**: 수동 테스트에서 두 번 연속 실행(약 3.75분 간격)했을 때 `velocityScore`가 계속 `null`로 나와서 처음엔 버그로 의심했다. 실제로는 `MIN_ELAPSED_HOURS` 가드가 의도대로 노이즈 구간을 걸러낸 것이었다 — 스냅샷 타임스탬프를 직접 조회해 경과 시간이 6분 미만임을 확인하고 정상 동작임을 확인함. 실제 1시간 주기 스케줄에서는 문제없이 계산됨.

> 2차 개편 이후: `velocity.ts`는 삭제했다. `TrendItem.youtubeVideoId`(영상 추적)는 그대로 쓰고, `velocityScore` 컬럼과 `VideoSnapshot` 테이블은 이후 스키마에서 삭제했다(15번 참고).

## 2. Gemini 무료 티어 Rate Limit (429) — 실제로 터진 버그

**문제점**
영상 제목·설명에서 키워드를 추출하는 `extractKeywords()` 호출을 25개 신규 영상에 대해 루프 안에서 연달아 호출했는데, 기존 `summarize.ts`에 있던 "호출 사이 4.1초 대기" 패턴을 빠뜨렸다. 그 결과 1차 실행에서 다수 영상이 `429 RESOURCE_EXHAUSTED`로 실패:

```
Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests,
limit: 15, model: gemini-3.5-flash-lite
```

사전에 웹 검색으로 추정했던 "분당 30회"보다 실제 한도가 더 낮았다(실측 15 RPM) — 공개 문서/블로그 추정치와 실제 한도가 다를 수 있다는 교훈.

**개선 결과**
- `youtube.ts`에 `GEMINI_CALL_DELAY_MS = 4100`과 호출 카운터를 추가해 Gemini 호출 사이에 4.1초 간격을 강제.
- 더 중요한 문제: 키워드 추출에 실패한 영상은 `youtubeVideoId`가 이미 DB에 존재해서 다음 실행부터 "기존 영상"으로 분류되어 **영원히 재시도되지 않는** 구조였다. 이를 막기 위해 기존 영상도 `videoKeywords` 연결 개수가 0이면 키워드 추출을 다시 시도하도록 로직을 추가(`needsKeywords = !existing || existing._count.videoKeywords === 0`).

**흐름**
1. 1차 실행 → 다수 429 에러, 그래도 수집 자체는 에러 삼키기(try/catch)로 안 죽고 계속 진행됨 → 25건 모두 생성은 됐지만 키워드가 빠진 영상 다수.
2. 딜레이 추가 + 백필 로직 추가 후 재실행 → 로그에 429 없이 전부 처리, DB 확인 결과 영상당 키워드 2~5개씩 정상 연결(`total keywords: 92`).

> 2차 개편 이후: 영상별 키워드 추출은 "제목 묶음 → 주제 추출" 1회 호출로 바뀌어 호출 수 자체가 크게 줄었다. 4.1초 딜레이(`GEMINI_CALL_DELAY_MS`)는 `apps/cron/src/lib/config.ts`로 옮겨 주제 요약 루프에서 계속 쓴다.

## 3. 비대화형 환경에서 `prisma migrate dev` 실행 불가

**문제점**
스키마에 필드 5개 + 테이블 3개를 추가하고 `npx prisma migrate dev`를 실행하니, unique 제약(`youtubeVideoId`) 경고에 대한 대화형 확인(y/n)을 요구했다. 에이전트 환경은 TTY가 없는 비대화형 셸이라 `stdin`으로 "y"를 흘려줘도 Prisma가 아예 "non-interactive environment"로 감지해 즉시 에러를 냄.

**개선 결과**
`prisma migrate dev` 대신 아래 조합으로 비대화형에서도 안전하게 마이그레이션 파일을 만들고 적용했다:
```bash
npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script > migration.sql
npx prisma migrate deploy
```
`migrate diff`는 순수하게 SQL 스크립트만 생성하므로 대화형 확인이 필요 없고, `migrate deploy`는 CI/배포용으로 설계되어 처음부터 비대화형을 전제로 한다.

**흐름**
1. `prisma/migrations/<timestamp>_add_velocity_tracking/` 폴더를 먼저 만들고
2. 그 안에 `migrate diff` 결과를 `migration.sql`로 저장
3. `prisma migrate deploy`로 적용 (정상적으로 "1 migration applied" 확인)

> 참고: 2차 개편(`topic_shorts_tracking`)은 nullable 컬럼 추가뿐이라 경고가 없어서 `prisma migrate dev`가 대화형 확인 없이 바로 통과했다. 경고가 생기는 변경(unique 추가, 컬럼 삭제 등)일 때만 위 우회 방법이 필요하다.

## 4. Windows 작업 스케줄러 등록 시 중첩 인용 문제

**문제점**
`schtasks /create /tr "..."`에 `cmd.exe /c "cd /d \"...\" && npm run collect"` 형태로 중첩 인용 문자열을 직접 넘기면, 경로에 한글/공백이 섞여 있어 인용 처리가 깨지기 쉬움.

**개선 결과**
중첩 인용을 피하기 위해 `apps/cron/run-collect.cmd` 래퍼 배치 파일을 만들어 `%~dp0`(배치 파일 자신의 경로)로 디렉터리를 이동한 뒤 `npm run collect`를 실행하도록 하고, 스케줄러에는 이 파일 경로 하나만 등록했다.
```bat
@echo off
cd /d "%~dp0"
npm run collect >> collect.log 2>&1
```
```powershell
schtasks /create /tn "WhyTteum-Collect" /tr "<경로>\run-collect.cmd" /sc hourly /mo 1 /f
```

**흐름**
1. 등록 후 `schtasks /query /tn "WhyTteum-Collect" /fo LIST /v`로 "Schedule Type: Hourly, Repeat Every: 1 Hour" 확인.
2. `schtasks /run /tn "WhyTteum-Collect"`로 즉시 1회 실행 → `collect.log`에 정상 수집 로그 확인.

> 2차 개편 이후에도 스케줄러는 1시간 주기 그대로 쓴다. 유튜브 검색 간격(4시간)은 코드에서 조절한다 (2부 7번 참고).

# 2부. 2차 개편: 쇼츠 주제 확산(채널 수) 랭킹

## 5. 랭킹 결과가 기획 의도와 어긋남 — 방향 전환의 계기

**문제점**
1차 개편 후 실제 화면을 본 결과, "쓰레드·인스타에서 핫한 **유튜버 A씨 논란** 같은 건 안 뜨고 이상한 것만 뜬다"는 피드백이 나왔다. 기획 의도는 "며칠~몇 주 동안 많이 노출되고 많이 찾는 것"이었는데, 실제 데이터를 확인해 보니 원인이 세 가지였다.

1. **데이터 출처가 잘못됨**
   - 유튜브 검색으로 해당 유튜버 이름을 최근 3일 조회하면 방송사 뉴스, 다른 유튜버, 이슈 채널 등 **서로 다른 채널 20곳**이 영상을 올리고 있었다. 그런데 DB에는 관련 데이터가 **0건**이었다.
   - `chart=mostPopular`(인기 급상승)는 아이돌 뮤비·게임·대형 공식 채널 위주다. 논란은 영상 하나가 터지는 게 아니라 중소 채널의 해설·뉴스 영상 수십 개로 퍼지기 때문에 차트에 잡히지 않는다.
   - Google Trends RSS는 몇 시간짜리 반짝 급상승만 잡아서 태국 복권 결과(`ตรวจหวย`) 같은 항목까지 섞였다.
2. **키워드 집계가 사실상 동작하지 않음**
   - 영상마다 따로 키워드를 뽑다 보니, 랭킹 상위 키워드 대부분이 영상 **1~2개에만** 연결돼 있었다.
   - 그래서 영상 하나에서 나온 "넷플릭스 / 혁준 / 꿀알바"가 똑같은 점수로 같이 올라왔다. 여러 출처를 합쳐서 세는 효과가 없었다.
3. **시간 단위가 너무 짧음**: 시간당 조회수 증가 속도는 "유행"이 아니라 "지금 이 순간 터진 영상"을 측정한다.

**교훈**
"인기 있는 영상 하나"와 "유행하는 주제"는 다른 대상이다. 유행은 **같은 주제를 얼마나 많은 서로 다른 채널이 다루는가**로 측정해야 한다.

## 6. 외부 데이터 소스 조사 — 쓸 수 없는 API가 대부분

**문제점**
"SNS에서 화제인 것", "많이 사는 것"을 직접 측정하려고 API를 조사했지만 대부분 막혀 있었다.

| 대상 | 결과 |
|---|---|
| Threads / Instagram | 트렌드·인기 게시물 조회용 공개 API 없음. 크롤링은 약관 위반 |
| TikTok | Research API는 학술·비영리 연구자 전용. Display API는 본인 계정 영상만. Creative Center는 공식 API 없음 |
| 네이버 검색 / 데이터랩 / 쇼핑인사이트 | **2026-07-31부로 개발자센터 신규 발급 종료** → NAVER API HUB(네이버 클라우드 플랫폼)로 이관 |
| 실제 구매량 | 공개 API 없음. 쿠팡 파트너스는 승인 필요, 무신사·올리브영은 API 없음 |

**함정: 네이버 개발자센터 화면에 API가 안 보임**
- 애플리케이션 등록 화면의 "사용 API" 목록에 네이버 로그인, 캘린더, 카페 같은 로그인 방식 API만 있고, 검색·데이터랩이 아예 없었다.
- 처음엔 UI 문제로 의심했지만, 실제로는 위의 신규 발급 종료 때문이었다. **외부 API는 기억이나 옛날 블로그 글보다 최신 공지를 먼저 확인해야 한다.**

**함정: 네이버 검색 API의 AI 활용 금지 약관 (2026-09-07 시행)**
- 검색 결과를 AI에 입력하거나 저장·캐싱하는 것을 금지한다.
- 이 프로젝트처럼 글 내용을 Gemini로 요약하는 구조와 정면으로 충돌한다.
- 나중에 붙인다면 "최근 며칠간 글 개수"만 점수에 쓰고, 글 내용은 저장하지도 AI에 넣지도 않아야 한다.

**결정**
네이버는 보류하고, 유튜브(쇼츠 포함) + 구글 트렌드만으로 먼저 개편했다. 틱톡에서 시작된 유행도 며칠 안에 유튜브 쇼츠로 넘어오는 경우가 많아서, 쇼츠를 "SNS 화제"의 대리 지표로 쓴다.

## 7. 새 수집 구조: 탐색 → 확장 → 갱신 → 요약

**설계**
`apps/cron/src/collectors/youtube.ts`가 4단계로 동작한다. 설정값은 `apps/cron/src/lib/config.ts`에 모았다.

1. **탐색** (`discover`)
   - `search.list`로 최근 48시간 영상을 이슈성 쿼리로 검색한다.
   - 쇼츠 위주(`videoDuration=short`) 4개 쿼리: `논란|근황|폭로`, `유행|챌린지|밈`, `요즘|난리|화제`, `신상|품절|핫한`
   - 해설·뉴스 영상용(`videoDuration=medium`) 1개 쿼리: `논란|근황|폭로`
   - 모은 제목(약 250개)을 Gemini `extractTopics`에 **한 번에** 넘겨서, 같은 대상을 다루는 영상끼리 주제(고유명사)로 묶는다.
2. **확장** (`expand`)
   - 탐색에서 많이 잡힌 주제 8개를 주제 이름으로 다시 검색한다(최근 7일, 길이 무관).
   - 제목·설명에 주제 이름이 실제로 들어간 영상만 연결한다(`mentionsTopic`).
   - 이 단계 덕분에 유튜버 A씨 논란이 탐색에서는 채널 4곳이었지만, 확장 후에는 **35곳**으로 잡혔다.
3. **갱신** (`refreshLinkedVideos`): 주제에 연결된 최근 30일 영상의 조회수를 `videos.list`로 갱신한다.
4. **요약** (`summarizeTopTopics`): 최근 7일 기준 채널 수 상위 주제부터, 관련 영상 제목(+같은 이름의 구글 트렌드 뉴스 제목)으로 "왜 뜨는지"를 요약해 `Keyword.summary`에 저장한다.

**랭킹** (`apps/web/src/lib/trends.ts`)
- 점수 = (서로 다른 채널 수 + 0.5 × 쇼츠 채널 수) × log10(10 + 총 조회수)
- 채널 수가 핵심이고, 조회수는 로그로 눌러서 보정용으로만 쓴다.
- 채널 1곳만 다룬 주제는 제외한다(`MIN_CHANNEL_COUNT = 2`).
- 기간은 영상 **업로드 시각**(`publishedAt`) 기준 3일 / 7일 / 30일.

**스키마** (마이그레이션 `topic_shorts_tracking`)
- `Keyword`를 "주제"로 재사용: `category`, `summary`, `summaryAt`, `lastExpandedAt` 추가
- `TrendItem`: `publishedAt`, `durationSec`, `isShort`(180초 이하) 추가
- 유튜브 API에는 "쇼츠 여부" 필드가 없어서 영상 길이로 판정한다.

## 8. YouTube API 할당량: 검색 1회 = 100 units

**문제점**
- `videos.list`는 1회 1 unit인데, `search.list`는 1회 **100 units**다. 하루 무료 할당량은 10,000 units.
- 작업 스케줄러가 1시간마다 도는데 매번 검색 13회(탐색 5 + 확장 8)를 하면 하루 31,200 units로 3배 초과한다.

**개선 결과**
- 스케줄러 주기는 그대로 두고, 코드에서 마지막 성공 실행 후 4시간(`DISCOVERY_INTERVAL_HOURS`)이 안 지났으면 유튜브 수집을 건너뛴다.
- 13회 × 100 units × 하루 6회 ≈ 7,800 units로 한도 안에 들어온다.
- 검색으로는 영상 ID만 받고(`part=id`), 길이·조회수·카테고리는 `videos.list`로 50개씩 묶어 조회해서 비용을 아꼈다.
- 수동 테스트용으로 `FORCE_DISCOVERY=1 npm run collect`를 두었다.

**함정: 건너뛴 실행도 "성공"으로 기록하면 영원히 건너뜀**
- 간격 판단은 `CollectionLog`의 마지막 SUCCESS 시각으로 한다.
- 건너뛴 실행까지 SUCCESS로 남기면 매시간 기록이 갱신돼서, 4시간이 영원히 지나지 않는다.
- 그래서 collector가 `{ skipped: true }`를 돌려주면 `index.ts`에서 로그를 남기지 않도록 했다.

## 11. 요약 대상이 순위와 무관하게 선택됨 — `findMany`의 `in` 순서

**문제점**
요약을 다시 생성했더니 상위 주제(채널 수 1~3위 주제)가 아니라 하위 주제부터 요약됐다.

**원인**
- 채널 수 순으로 정렬한 ID 목록(`topIds`)을 `prisma.keyword.findMany({ where: { id: { in: topIds } } })`로 다시 불러왔다.
- **`in` 조건은 결과 순서를 보장하지 않는다.** 그래서 정렬이 사라진 상태에서 `.slice(0, 10)`이 아무 10개나 골랐다.

**개선 결과**
불러온 뒤 `topIds.indexOf()` 기준으로 다시 정렬하고 나서 자르도록 고쳤다.
```ts
.sort((a, b) => topIds.indexOf(a.id) - topIds.indexOf(b.id))
```

## 12. 구글 트렌드 검색어를 확장 후보로 넣었더니 잡음 유입

**문제점**
처음에는 구글 트렌드 급상승 검색어(검색량 1,000 이상, 최대 2개)도 유튜브 확장 검색 후보로 넣었다. "검색에서 뜬 것을 유튜브 확산으로 검증한다"는 의도였다. 그런데 두 번째 실행에서 이런 주제가 상위권에 올라왔다.
- **"시어머니"**: 일반 단어인데 채널 37곳(드라마 썰 쇼츠가 많아서)

**개선 결과**

- 이미 들어간 두 주제와 연결 데이터는 삭제했다.

## 13. 랭킹이 뉴스처럼 보임 — 카테고리를 "유행"으로 좁힘

**문제점**
- 이슈성 쿼리(`논란|근황|폭로`) 특성상 정치 주제가 랭킹 상위권을 많이 차지했다.
- 카테고리 필터와 최신순 피드가 있던 "전체 트렌드" 페이지(`/all`)는 수집된 영상을 그대로 나열해서, 유행 서비스라기보다 뉴스 피드처럼 보였다.
- Gemini 분류 카테고리도 사회/이슈, IT/과학, 스포츠처럼 유행과 관계없는 것이 섞여 있었다.

**개선 결과**
- **카테고리를 유행 중심으로 재정의**: 음식/디저트, 패션/뷰티, 아이템/쇼핑, 밈/챌린지, 음악/댄스, 드라마/예능, 게임, 인물/이슈(유튜버·연예인), 정치
  - cron: `apps/cron/src/lib/gemini.ts`의 `TOPIC_CATEGORIES`
  - web: `apps/web/src/lib/ranking-config.ts`의 `TREND_CATEGORIES` (이모지 포함, 두 목록을 맞춰서 유지)
- **"제외" 분류 추가**: 사회 뉴스(사건·사고), 스포츠 경기 결과, 해외 뉴스는 Gemini가 "제외"로 분류하면 주제로 저장하지도, 확장 검색하지도 않는다. 확장 검색 할당량을 유행 주제에만 쓰게 된다.
- **정치는 따로 분리**: 관심 있는 사람이 많아 버리지 않고 "정치" 카테고리로 저장한다. 다만 메인 전체 랭킹에서는 빼고(`HIDDEN_FROM_ALL_CATEGORIES`), 카테고리별 유행 페이지에서만 보인다.
  - *(이후 변경)* 정치 카테고리는 아예 없앴다. 사이트 목적(유행)과 맞지 않아서 Gemini가 정치 주제를 "제외"로 분류해 버리고, 예전에 정치로 저장된 주제는 웹 카테고리 목록에 없어서 보이지 않는다.
- **탐색 쿼리 조정**: 해설·뉴스용 medium 쿼리를 빼고, 음식(`디저트|신메뉴|맛집`)과 패션(`코디|화장품|올리브영`) 쇼츠 쿼리를 추가했다(검색 6 + 확장 8 = 하루 약 8,400 units).
- **페이지 정리**: `/all`, `/trend/[id]`와 관련 컴포넌트를 삭제했다. 대신 `/categories`(카테고리별 유행)를 추가했다. 기본은 카테고리마다 이번 주 랭킹 카드, 칩을 고르면 그 카테고리의 3일/7일/30일 랭킹을 보여준다.
- **기존 데이터 이관**: 옛 카테고리를 SQL로 새 카테고리에 매핑했다(예: 인물/유튜버 → 인물/이슈, 영화/드라마 → 드라마/예능). 매핑되지 않는 것은 "제외"로 옮겼다.

**함정: 기존 주제의 카테고리가 갱신되지 않음**
- `TopicRegistry.findOrCreate`는 기존 주제의 카테고리가 비어 있을 때만 새 분류를 반영했다.
- 그래서 한 번 "제외"로 분류된 주제는 나중에 유행 카테고리로 다시 분류돼도 영원히 화면에 나오지 않는 구조였다.
- 가장 최근 분류를 따르도록 바꿨다.

## 14. 개발 서버가 갑자기 `Jest worker encountered 2 child process exceptions`

**문제점**
코드를 건드리지 않았는데 페이지를 열면 서버 에러가 났다. 개발 서버 로그(`apps/web/.next/dev/logs/next-development.log`)에는 아래 에러가 반복됐다.
```
Error: write EPIPE
⨯ "uncaughtException:" Error: write EPIPE
⨯ Error: Jest worker encountered 2 child process exceptions, exceeding retry limit
```

**원인**
- 개발 서버를 띄운 터미널(백그라운드 작업)이 시간 제한으로 먼저 종료됐는데, Next.js 프로세스는 죽지 않고 남아 있었다.
- 로그를 내보낼 출력 통로(stdout)가 닫힌 상태라, 서버가 로그를 쓸 때마다 `EPIPE`가 났다.
- 그 여파로 페이지를 렌더링하는 작업자 프로세스가 연달아 죽었다. "Jest worker"는 Next.js가 내부적으로 쓰는 작업자 라이브러리 이름이라, 테스트 코드와는 관계없다.
- 같은 상태에서 서버를 새로 띄우려 하면 "이미 3000번 포트에서 실행 중"이라며 바로 종료된다.

**개선 결과**
남아 있던 `next` node 프로세스를 모두 종료하고 서버를 다시 띄우니 정상화됐다. **터미널을 닫거나 작업이 끊긴 뒤 서버가 이상하면, 먼저 남은 node 프로세스가 있는지 확인한다.**

## 15. 모노레포 정리: npm workspaces 전환 + 옛 스키마 제거

**문제점**
- `node_modules`가 루트, `apps/web`, `apps/cron`에 하나씩 총 3개, `package-lock.json`도 3개였다.
- Prisma는 루트에만 설치하고, 하위 앱은 Node.js가 상위 폴더를 거슬러 올라가며 패키지를 찾는 동작에 기대서 공유하고 있었다. 동작은 하지만 의도가 드러나지 않는 구조였다.
- 1차 개편(velocity)의 흔적인 컬럼·테이블이 스키마에 남아 있었다.

**개선 결과**
- 루트 `package.json`에 `"workspaces": ["apps/*"]`를 추가하고, 앱별 `node_modules`와 lock 파일을 지운 뒤 루트에서 `npm install` 한 번으로 다시 설치했다. 이제 `node_modules`와 `package-lock.json`이 각각 1개다.
- 루트에서 `npm run dev`, `npm run collect`, `npm run summarize`로 각 앱 명령을 실행할 수 있게 했다. 작업 스케줄러의 `apps/cron/run-collect.cmd`(앱 폴더에서 `npm run collect`)도 그대로 동작한다. npm이 상위 폴더의 `node_modules/.bin`까지 찾아주기 때문이다.
- 스키마에서 `velocityScore`, `subscriberCount`, `isOfficialChannel` 컬럼과 `VideoSnapshot`, `AiSummary` 테이블, 쓰지 않는 `NAVER_DATALAB` 값을 지웠다. 데이터 삭제 경고가 뜨는 변경이라 3번의 `migrate diff` + `migrate deploy` 방식으로 적용했다(마이그레이션 `remove_legacy_velocity_fields`).
- 함께 정리: Next.js 기본 템플릿 파일(`public/*.svg`, `apps/web/README.md`), 호출하는 곳이 없던 영상별 요약 함수(`summarizeTrend`).

## 16. 카테고리가 제 기능을 못 함 — 사람이 음식/디저트에, 배우가 음악/댄스에

**문제점**
- 음식/디저트 카테고리에 음식과 관계없는 사람이 올라오고, 음악/댄스에 열애설이 난 배우가 올라왔다.
- 득표제와 분류 기준 정리(카테고리별 설명 + "영상 내용이 아니라 대상 자체로")를 넣은 뒤에도 같은 일이 생겼다. Gemini(lite)가 제목 100여 개를 한 번에 묶으면서 "음악/댄스", "인물/이슈"처럼 경계가 애매한 **카테고리 이름**을 직접 골랐기 때문이다. 영상 맥락(디저트 먹방, 아이돌과의 열애설)에 끌려가서 틀렸고, 같은 모델이 매번 비슷하게 틀리니 득표를 쌓아도 틀린 쪽이 다수가 됐다.

**개선 결과**
- Gemini에는 카테고리 대신 **대상의 종류(type)**만 고르게 했다: 가수, 배우, 방송인, 유튜버, 음식/음료, 작품, 물건 등. 종류에서 카테고리로의 매핑은 코드(`TOPIC_TYPES`)가 한다. "이 대상이 사람인가, 사람이면 직업이 뭔가"는 모델이 훨씬 안정적으로 답하고, 사람 종류는 음식/디저트로 매핑될 길이 없어서 구조적으로 막힌다.
- 정치인, 정치 이슈, 사건·사고, 스포츠 경기, 해외뉴스, 기타는 "제외"로 매핑해서 저장하지 않는다.
- 헷갈리는 예시(디저트 먹방을 한 배우, 열애설이 난 배우, 탕후루 먹방을 한 아이돌, 편의점 리뷰를 한 유튜버, 페이커 등) 12개로 재분류를 확인했고 lite와 flash 모두 12/12를 맞혔다. 주제 추출 경로에서도 같은 결과가 나왔다.
- **요약 시점에 카테고리 확정**: 상위 주제는 요약을 만들 때(상위 모델, 주제 하나의 영상 제목 20개) "왜 뜨는지"를 먼저 쓰고 그 내용을 바탕으로 종류도 고르게 했다. 응답은 `{"summary", "type"}` JSON이다. 이 분류로 카테고리를 확정하고 득표를 `CONFIRMED_CATEGORY_WEIGHT`(3표)로 초기화한다. 요약 호출에 붙인 거라 Gemini 호출 수는 늘지 않는다. 요약이 갱신될 때(24시간)마다 다시 확정된다. 요약이 없는 하위 주제는 탐색 단계의 lite 분류를 따른다.
  - 예전에는 요약 프롬프트에 기존 카테고리를 넣었는데, 틀린 카테고리가 판단을 끌고 갈 수 있어서 뺐다.
- 기존 주제는 `npm run reclassify -w cron`으로 새 기준에 맞춰 다시 분류한다. 득표가 새 분류 3표로 초기화된다.

## 남은 한계

- **AI 요약의 사실관계 오류**: 유튜버 A씨 논란 요약에서 가해·피해 관계가 뒤바뀐 문장("A씨가 전 연인으로부터 … 당했다는 폭로")이 반복해서 나왔다. 원인은 '"OO당했다" 전 연인의 폭로' 같은 뉴스 제목에서 따옴표 안의 말이 누구의 말인지 모델이 헷갈리는 것으로 보인다. 프롬프트에 "주체를 뒤바꾸지 말 것" 규칙과 예시를 넣고, 요약 모델을 lite에서 `gemini-3.5-flash`(`GEMINI_SUMMARY_MODEL`)로 올렸지만 생성할 때마다 결과가 달라 완전히 막지 못했다. 공개 서비스라면 논란 주제는 요약 대신 관련 영상만 보여주거나, 요약 검증 단계를 추가해야 한다. 현재는 상세 페이지와 푸터에 "AI 요약은 사실과 다를 수 있어요" 안내만 있다.
- **카테고리 분류 정확도**: 종류 기반 분류(16번)로 많이 줄었지만 여전히 Gemini 판단에 기댄다. 가수 겸 배우처럼 종류 자체가 애매한 대상은 고르는 쪽이 갈릴 수 있다.
- **확장 순서 편향**: 한 번에 8개 주제만 확장하기 때문에, 아직 확장되지 않은 주제는 채널 수가 적게 잡힌다. 실행이 몇 번 반복되면 완화된다.
- **채널 수 기준의 약점**: 같은 소속사·방송사의 여러 채널이 같은 주제를 다루면 채널 수가 부풀 수 있다.

## 참고: 1차 개편의 카테고리 디레이팅 *(2차 개편에서 제거)*

1차 개편에서는 Music 카테고리 제외와 구독자 100만 이상 "공식 채널" 가중치 0.3을 **랭킹 조회 시점**(`apps/web/src/lib/trends.ts`)에 적용했다. 수집 데이터는 그대로 두고 기준값만 랭킹 쿼리에서 바꿀 수 있게 하려는 설계였다.

2차 개편에서는 둘 다 제거했다. 채널 수 기준에서는 소속사가 자기 채널에 쇼츠를 10개 올려도 "채널 1곳"으로만 세지기 때문에, 공식 채널이 랭킹을 독점하는 문제가 구조적으로 사라졌다. 그래서 채널 구독자 조회(`channel.ts`)도 삭제했다. "수집은 그대로, 기준은 조회 시점에" 원칙은 2차 개편의 점수 계산에도 그대로 이어진다.
